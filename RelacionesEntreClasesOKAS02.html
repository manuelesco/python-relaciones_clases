Relaciones Entre Clases

Cómo se conectan las clases para colaborar y reutilizar código.

🔗 Relaciones entre clases

En la programación orientada a objetos, las clases rara vez existen de forma aislada. Lo más natural es que colaboren, se organicen y compartan responsabilidades entre sí. A eso se le llama relaciones entre clases, y es uno de los pilares del diseño orientado a objetos.

Python ofrece varios mecanismos para establecer estas relaciones. En este curso, se verán las siguientes: Composición, Herencia Simple y Herencia Múltiple.

¿Por qué importan las relaciones entre clases?

Cuando un programa crece, organizar el código en clases independientes y sin relación entre sí se vuelve inviable. Las relaciones permiten:

  • Reutilizar código sin duplicarlo.
  • Modelar el mundo real de forma natural (un auto tiene un motor, un perro es un animal).
  • Reducir el acoplamiento, haciendo el código más fácil de mantener y extender.

Los tres tipos que verás en este curso:

Composición — una clase contiene instancias de otras clases como atributos. La relación se lee como "tiene un": un Auto tiene un Motor. Es la forma más flexible de combinar comportamientos.

Herencia simple — una clase hereda atributos y métodos de una sola clase padre. La relación se lee como "es un": un Perro es un Animal. Permite extender y especializar comportamientos existentes.

Herencia múltiple — una clase puede heredar de más de una clase padre simultáneamente.

Cada uno de estos mecanismos tiene sus casos de uso, ventajas y consideraciones de diseño

📂

🧩 Composición

Relación: "tiene un"

La composición es un principio de diseño orientado a objetos donde una clase se construye incluyendo instancias de otras clases como atributos. Modela relaciones del tipo "tiene un" (has-a).

La composición es un principio de diseño orientado a objetos donde una clase se construye utilizando instancias de otras clases como componentes. A diferencia de la herencia, que define una relación de "es un", la composición define una relación de "tiene un".

La Composición es un principio de diseño de la Programación Orientada a Objetos (POO) donde una clase compleja se construye combinando uno o más objetos de otras clases como parte de sus atributos.

En lugar de heredar comportamientos de una clase padre, la clase "compuesta" delega la responsabilidad a los objetos internos que ha instanciado. Esto permite crear sistemas más flexibles, modulares y fáciles de mantener. La composición permite crear sistemas complejos combinando objetos más simples y especializados.

📝 Nota:

La composición favorece la reutilización de código sin crear jerarquías de herencia rígidas.

🛠️ Sintaxis:

La composición se logra simplemente instanciando las clases componentes dentro del método __init__ de la clase contenedora o compuesta. 

class ComponenteA:
    def método_componente_a(self):
        # Atributos del componenteA
		pass

class ComponenteB:
    def método_componente_b(self):
        # Atributos del componenteB
		pass

class ComponenteN:
    def método_componente_N(self):
        # Atributos del componente
		pass

class Contenedor:
    def __init__(self):
		# Se crea la instancia de cada clase Componente dentro de Contenedor
        self.comp_a = ComponenteA()
        self.comp_b = ComponenteB()
		self.comp_n = ComponenteN()
	
	def método_contenedor(self):
        # Se delega la tarea a los componentes
        self.atributo_componente.método_componente_a()
        self.atributo_componente.método_componente_b()
        self.atributo_componente.método_componente_n()

La clase Contenedor posee instancias de ComponenteA, ComponenteB y ComponenteN. Son parte integral de su existencia.

💻 Ejemplo:

Python ejemplo 
class Motor:
    def __init__(self, cilindros: int, combustible: str):
        self.cilindros = cilindros
        self.combustible = combustible

    def encender(self) -> str:
        return f"Motor de {self.cilindros} cilindros encendido ({self.combustible})"

    def apagar(self) -> str:
        return "Motor apagado"


class Coche:
    def __init__(self, marca: str, modelo: str):
        self.marca = marca
        self.modelo = modelo
		# Aquí ocurre la composición: el Coche "tiene un" Motor
        self.motor = Motor(4, "gasolina")

    def arrancar(self) -> str:
		# Delegación de comportamiento con self.motor.encender()
        return f"{self.marca} {self.modelo}: {self.motor.encender()}"

    def detener(self) -> str:
		# Delegación de comportamiento con self..motor.apagar()
        return f"{self.marca} {self.modelo}: {self.motor.apagar()}"


mi_coche = Coche("Toyota", "Corolla")
print(mi_coche.arrancar())   
print(mi_coche.detener())
salida 
Toyota Corolla: Motor de 4 cilindros encendido (gasolina)
Toyota Corolla: Motor apagado
💡 Tip:

Si el Coche se destruye, el Motor también desaparece. Eso es composición fuerte (el ciclo de vida del componente depende del contenedor).

💡 Tip:

La composición permite cambiar el componente en tiempo de ejecución. Podrías cambiar el objeto self.motor por un MotorElectrico sin necesidad de cambiar toda la jerarquía de la clase Coche.

class CPU:
    def __init__(self, marca: str, nucleos: int):
        self.marca = marca
        self.nucleos = nucleos

    def procesar(self) -> str:
        return f"CPU {self.marca} ({self.nucleos} núcleos) procesando"


class RAM:
    def __init__(self, capacidad_gb: int):
        self.capacidad_gb = capacidad_gb

    def estado(self) -> str:
        return f"RAM {self.capacidad_gb}GB activa"


class Disco:
    def __init__(self, capacidad_tb: float, tipo: str):
        self.capacidad_tb = capacidad_tb
        self.tipo = tipo

    def estado(self) -> str:
        return f"Disco {self.tipo} {self.capacidad_tb}TB montado"


class Computadora:
    def __init__(self, nombre: str):
        self.nombre = nombre
        self.cpu   = CPU("Intel", 8)
        self.ram   = RAM(16)
        self.disco = Disco(1.0, "SSD")

    def reporte(self) -> str:
        lineas = [
            f"=== {self.nombre} ===",
            self.cpu.procesar(),
            self.ram.estado(),
            self.disco.estado(),
        ]
        return "\n".join(lineas)


pc = Computadora("WorkStation-01")
print(pc.reporte())
salida 
=== WorkStation-01 ===
CPU Intel (8 núcleos) procesando
RAM 16GB activa
Disco SSD 1.0TB montado

Herencia

Relación "es un"

La herencia es uno de los pilares fundamentales de la programación orientada a objetos. La idea central es sencilla: una clase puede adquirir los atributos y métodos de otra clase, evitando repetir código y permitiendo construir jerarquías lógicas entre conceptos.

La relación se lee siempre como "es un": un Perro es un Animal, un Empleado es una Persona. Si esa frase tiene sentido, la herencia probablemente es la herramienta correcta.

🧑‍👦

Herencia Simple

Una clase deriva de otra.

La herencia simple es uno de los pilares fundamentales de la Programación Orientada a Objetos (POO). Permite crear una nueva clase a partir de una clase ya existente, heredando sus atributos y métodos.

La clase existente se denomina clases base ( o clase padre o superclase) y la nueva clases se denomina clase derivada (o clase hija o subclase).

Cuando hablamos de Herencia Simple, nos referimos específicamente a que la clase hija solo puede heredar de una única clase padre.

La Herencia Simple es un principio de la Programación Orientada a Objetos (POO) que permite que una clase nueva (denominada clase hija o subclase) derive sus atributos y métodos de una clase ya existente (denominada clase padre o superclase).
En términos sencillos, la clase hija "hereda" todo el comportamiento de la clase padre, permitiendo extender su funcionalidad o modificarla sin tener que reescribir el código.

La herencia simple se basa en la relación "es un". Por ejemplo: un Perro es un Animal.

  • Clase Base: Es la clase original que contiene la lógica general.
  • Clase Derivada: Es la clase que hereda de la clase base y puede añadir sus propias características únicas.

🛠️ Sintaxis básica:

# Definición de la Clase Padre
class ClasePadre:
    # atributos y métodos del padre
    pass

# Definición de la Clase Hija (Hereda de ClasePadre)
class ClaseHija(ClasePadre):
    # Atributos y métodos adicionales o sobreescritos
    pass

# Clase Padre
class Animal:
    def __init__(self, nombre):
        self.nombre = nombre

    def comer(self):
        return f"{self.nombre} está comiendo."

# Clase Hija (Hereda de Animal)
class Perro(Animal):
    def ladrar(self):
        return f"{self.nombre} dice: ¡Guau!"

# --- Uso del código ---
# Instanciamos la clase hija
mi_perro = Perro("Toby")

# Accedemos a un método heredado de la clase Padre
print(mi_perro.comer())  # Salida: Toby está comiendo.

# Accedemos a un método propio de la clase Hija
print(mi_perro.ladrar()) # Salida: Toby dice: ¡Guau!
salida 
Toby está comiendo.
Toby dice: ¡Guau!

Perro no tiene el método comer(), pero lo puede usar porque lo heredó automáticamente de Animal

🔍 Verificar herencia

Dos funciones útiles para inspeccionar la jerarquía: 

print(isinstance(mi_perro, Perro))     # True → mi_perro es instancia de Perro
print(isinstance(mi_perro, Animal))    # True → mi_perro también es instancia de Animal
print(issubclass(Perro, Animal))  # True → Perro es subclase de Animal

📌 super() — Acceder al padre

super() es una función integrada (built-in) que permite llamar a métodos definidos en una clase padre desde una clase hija, especialmente útil en __init__.

A menudo, la clase hija no solo quiere usar lo de la clase padre, sino que necesita sus propios atributos en (__init__). Para evitar reescribir el código del padre, usamos la función super().


Sintaxis con super():

class Hijo(Padre):
    def __init__(self, atributo_padre, atributo_hijo):
        super().__init__(atributo_padre)   # Llama al inicializador del padre
        self.atributo_hijo = atributo_hijo # Atributo propio

💻 Ejemplo:

Python ejemplo 
class Animal:
    def __init__(self, nombre, edad):
        self.nombre = nombre
        self.edad = edad

class Gato(Animal):
    def __init__(self, nombre, edad, color):
	    # Inicializamos los atributos de la clase padre
        super().__init__(nombre, edad)   # inicializa nombre y edad desde Animal
		# Añadimos el atributo específico de la clase hija
        self.color = color               # atributo propio de Gato

misifus = Gato("Misifús", 3, "gris")
print(misifus.nombre)   
print(misifus.edad)     
print(misifus.color)
salida 
Misifús
3
gris
⚠️ Precaución:

Si la clase hija define __init__ sin llamar a super(). __init__(), los atributos del padre no se inicializan y obtendrás un AttributeError al intentar acceder a ellos.

✏️ Sobreescritura de métodos (Overriding)

La sobreescritura ocurre cuando una clase hija define un método con el mismo nombre que uno de su clase padre, pero con una implementación distinta. Al llamar al método sobre un objeto de la clase hija, Python ejecuta la versión de la hija, no la del padre.

Esto permite que las clases hijas especialicen o adapten el comportamiento heredado.

🛠️ Sintaxis básica: 

class Padre:
    def metodo(self):
        print("Método de la clase Padre")


class Hija(Padre):          # Herencia simple: una sola clase padre
    def metodo(self):       # Mismo nombre → sobreescritura
        print("Método de la clase Hija")


obj = Hija()
obj.metodo()   # Salida: Método de la clase Hija

Python busca el método primero en la clase del objeto (Hija). Si lo encuentra, lo usa; si no, sube a la clase padre.

💻 Ejemplo:

Python ejemplo 
class Animal:
    def __init__(self, nombre):
        self.nombre = nombre

    def hablar(self):
        print(f"{self.nombre} hace un sonido")

    def presentarse(self):
        print(f"Soy {self.nombre}")


class Perro(Animal):
    def hablar(self):                  # Sobreescribe hablar()
        print(f"{self.nombre} dice: ¡Guau!")


class Gato(Animal):
    def hablar(self):                  # Sobreescribe hablar()
        print(f"{self.nombre} dice: ¡Miau!")


animales = [Animal("Genérico"), Perro("Rex"), Gato("Michi")]

for a in animales:
    a.hablar()
    a.presentarse()   # No fue sobreescrito: usa el del padre
salida 
Genérico hace un sonido
Soy Genérico
Rex dice: ¡Guau!
Soy Rex
Michi dice: ¡Miau!
Soy Michi

Observa que presentarse() no se sobreescribió, así que se hereda tal cual.

💡Tip:

Puedes sobreescribir y reutilizar el comportamiento original del padre combinando la sobreescritura con super(): 

class Perro(Animal):
    def hablar(self):
        super().hablar()        # ejecuta el método del padre primero
        print("¡Guau también!")

...
¡Guau también!

🪗 Extender en lugar de reemplazar

Muchas veces no quieres descartar por completo el comportamiento del padre, sino ampliarlo. Para eso se usa super(), que da acceso a los métodos de la clase padre.

💻 Ejemplo:

Python ejemplo 
class Empleado:
    def __init__(self, nombre, salario):
        self.nombre = nombre
        self.salario = salario

    def descripcion(self):
        return f"{self.nombre} gana ${self.salario}"


class Gerente(Empleado):
    def __init__(self, nombre, salario, departamento):
        super().__init__(nombre, salario)     # Reutiliza el __init__ del padre
        self.departamento = departamento

    def descripcion(self):
        base = super().descripcion()          # Llama a la versión del padre
        return f"{base} y dirige {self.departamento}"


g = Gerente("Ana", 5000, "Ventas")
print(g.descripcion())
salida 
Ana gana $5000 y dirige Ventas

Nota que __init__ también es un método y se puede sobreescribir; es el caso más común.

🔑 Puntos importantes:

  1. Mismo nombre: Python no distingue por tipo ni cantidad de parámetros. Solo importa el nombre del método.
  2. Firma compatible: aunque Python no lo exige, es buena práctica mantener los mismos parámetros que el método original, para que el objeto hijo pueda usarse donde se espera el padre.
  3. super(): úsalo para reutilizar la lógica del padre y no duplicar código.
  4. Polimorfismo: la sobreescritura es la base del polimorfismo, ya que puedes llamar al mismo método sobre objetos de distintas clases y cada uno responde a su manera (como en el ciclo de animales).
  5. Llamada explícita alternativa: también puedes invocar al padre con Padre.método(self), pero super() es la forma recomendada.
📝 Nota: Sobreescritura vs. sobrecarga

Python no soporta sobrecarga tradicional (varios métodos con el mismo nombre y distinta firma en la misma clase). Si defines dos métodos con el mismo nombre en una clase, el último reemplaza al anterior. La sobreescritura, en cambio, es entre clase padre e hija.

♿ Accesibilidad de atributos

En Python no existen modificadores de acceso estrictos (como private o protected en Java o C++). En su lugar se usan convenciones de nombres y un mecanismo llamado name mangling. La herencia simple es cuando una clase hija hereda de una sola clase padre.

Tipo Sintaxis ¿Accesible? ¿Heredado?

"Protegido"
(convención)		 self._nombre Técnicamente sí, pero no se debe Sí

🟢 Atributos públicos

Se heredan y se pueden usar libremente en la clase hija y desde fuera.

💻 Ejemplo:

class Animal:
    def __init__(self, nombre):
        self.nombre = nombre          # público

class Perro(Animal):
    def ladrar(self):
        return f"{self.nombre} dice: ¡Guau!"

p = Perro("Rex")
print(p.nombre)    # Rex
print(p.ladrar())  # Rex dice: ¡Guau!

🟡 Atributos "protegidos" (un guion bajo)

El guion bajo simple es solo una convención: indica "uso interno, pensado para la clase y sus subclases". Python no lo impide.

💻 Ejemplo:

class Animal:
    def __init__(self, edad):
        self._edad = edad             # protegido por convención

class Perro(Animal):
    def cumpleaños(self):
        self._edad += 1               # correcto: la subclase sí puede usarlo
        return self._edad

p = Perro(3)
print(p.cumpleaños())  # 4
print(p._edad)         # 4 -> funciona, pero se considera mala práctica

🔴 Atributos "privados" (dos guiones bajos)

Python aplica name mangling: renombra internamente __atributo a _NombreClase__atributo. Esto hace que la subclase no lo encuentre con su nombre original.

💻 Ejemplo:

class Animal:
    def __init__(self, secreto):
        self.__secreto = secreto      # se convierte en _Animal__secreto

    def revelar(self):
        return self.__secreto         # dentro de Animal funciona

class Perro(Animal):
    def intentar_acceder(self):
        return self.__secreto         # busca _Perro__secreto -> no existe

perro = Perro("hueso enterrado")
print(perro.revelar())                # hueso enterrado (vía método de la clase padre)

# print(perro.intentar_acceder())     # return self.__secreto         # busca _Perro__secreto -> no existe

# print(perro.__secreto)              # AttributeError: 'Perro' object has no attribute '_Perro__secreto'

⚠️ Precaución:

Acceder a _Padre__atributo desde la hija es técnicamente posible pero rompe el encapsulamiento intencionado por el diseñador de la clase padre. Evítalo.

🤔 ¿Para qué sirve el name mangling?

Evita que una subclase sobrescriba por accidente un atributo de la clase padre:

💻 Ejemplo:

class Base:
    def __init__(self):
        self.__valor = "de Base"
    def mostrar_base(self):
        return self.__valor

class Hija(Base):
    def __init__(self):
        super().__init__()
        self.__valor = "de Hija"     # es otro atributo: _Hija__valor
    def mostrar_hija(self):
        return self.__valor

h = Hija()
print(h.mostrar_base())  # de Base
print(h.mostrar_hija())  # de Hija
print(h.__dict__)        # {'_Base__valor': 'de Base', '_Hija__valor': 'de Hija'}

Coexisten los dos atributos sin pisarse. Con un atributo público o protegido, la hija habría sobrescrito el valor de la base.

⚔️ Atributos de clase vs. atributos de instancia

Las mismas reglas de acceso aplican a atributos de clase, que además son compartidos:

💻 Ejemplo:

class Vehiculo:
    ruedas = 4            # público
    _marca = "Genérica"   # protegido
    __serie = "X123"      # privado

class Coche(Vehiculo):
    def info(self):
        return self.ruedas, self._marca

c = Coche()
print(c.info())                  # (4, 'Genérica')
print(Vehiculo._Vehiculo__serie) # X123 (por mangling)

Coexisten los dos atributos sin pisarse. Con un atributo público o protegido, la hija habría sobrescrito el valor de la base.

✨ Buena práctica: usar propiedades

Para controlar el acceso de forma más seria, se usa @property:

💻 Ejemplo:

class Cuenta:
    def __init__(self, saldo):
        self._saldo = saldo

    @property
    def saldo(self):             # solo lectura
        return self._saldo

class CuentaAhorro(Cuenta):
    def agregar_interes(self):
        self._saldo *= 1.05

c = CuentaAhorro(1000)
c.agregar_interes()
print(c.saldo)       # 1050.0
# c.saldo = 5        # AttributeError: no tiene setter

Coexisten los dos atributos sin pisarse. Con un atributo público o protegido, la hija habría sobrescrito el valor de la base.

✅ Buenas prácticas

  • Usa herencia cuando la relación es "es un/a" (Perro es un Animal). Si la relación es "tiene un/a", usa composición.
  • Llama siempre a super().__init__() en el __init__ de la hija para no romper la cadena de inicialización.
  • Para extender el comportamiento del padre, sobreescribe sus métodos y llama a super(). Evita modificar directamente sus atributos: si el padre cambia su implementación, tu clase hija dejaría de funcionar.
  • No abuses de las cadenas de herencia muy profundas (más de 3 niveles suele ser señal de diseño complejo).

Herencia Múltiple

Una clase deriva de varias

La herencia múltiple es una característica de la programación orientada a objetos (POO) donde una clase hija o derivada puede heredar atributos y métodos de más de una clase padre.

Esto permite reutilizar código de diferentes fuentes y combinar comportamientos. Sin embargo, introduce complejidad, especialmente cuando dos o más superclases tienen métodos con el mismo nombre. Python resuelve esto de manera determinista utilizando el MRO (Method Resolution Order).

🛠️ Sintaxis básica:

Para indicar que una clase hereda de múltiples padres, simplemente se listan los padres entre paréntesis después del nombre de la clase hija, separadas por comas. 

class ClasePadre1:
    # Atributos y métodos de la primera clase
    pass

class ClasePadre2:
    # Atributos y métodos de la segunda clase
    pass

class ClaseHija(ClasePadre1, ClasePadre2):
    # Hereda de Padre1 y Padre2
    pass

🔷 Herencia Múltiple en UML

La notación es la misma que en la herencia simple: generalización (línea continua con triángulo hueco △ en el extremo del padre). La diferencia es que la clase hija tiene dos o más flechas, una hacia cada clase padre.

💻 Ejemplo:

Python ejemplo 
class Volador:
    def volar(self):
        return "Estoy volando."

class Nadador:
    def nadar(self):
        return "Estoy nadando."

# Clase hija que hereda de ambas
class Pato(Volador, Nadador):
    def graznar(self):
        return "¡Cuac, cuac!"

# Instanciación y uso
mi_pato = Pato()
print(mi_pato.volar())   # Heredado por Volador
print(mi_pato.nadar())   # Heredado por Nadador
print(mi_pato.graznar()) # Método propio
salida 
Estoy volando.
Estoy nadando.
¡Cuac, cuac!

Pato obtiene las capacidades de ambas clases sin repetir código.

🌿 Orden de Resolución de Métodos:

Si dos padres tienen un método con el mismo nombre, Python necesita decidir cuál usar. Para eso existe el MRO (Method Resolution Order, Orden de Resolución de Métodos).

💻 Ejemplo:

class A:
    def saludar(self):
        print("Hola desde A")

class B:
    def saludar(self):
        print("Hola desde B")

class C(A, B):
    pass

C().saludar()  # Hola desde A

Python busca de izquierda a derecha en la lista de padres, así que gana A. Puedes ver el orden completo así: 

print(C.__mro__)
(<class '__main__.C'>, <class '__main__.A'>, <class '__main__.B'>, <class 'object'>)

# o también:
print(C.mro())
(<class '__main__.C'>, <class '__main__.A'>, <class '__main__.B'>, <class 'object'>)
📝 Nota:

Toda clase en Python hereda implícitamente de object. Por eso object siempre aparece al final del MRO.

🏷️ Argumentos con nombre

Un argumento por nombre (keyword argument) es aquel en el que, al llamar a una función, indicas explícitamente a qué parámetro corresponde cada valor, usando la forma nombre=valor.


💻️ Ejemplo: Argumentos posicionales vs por nombre

def presentar(nombre, edad, ciudad):
    print(f"{nombre}, {edad} años, de {ciudad}")

# Posicionales: importa el ORDEN
presentar("Ana", 30, "CDMX")

# Por nombre: importa el NOMBRE, no el orden
presentar(ciudad="CDMX", nombre="Ana", edad=30)

Ambas llamadas dan el mismo resultado. Con argumentos por nombre puedes cambiar el orden libremente.

⚙️ **kwargs

**kwargs permite que una función reciba cualquier cantidad de argumentos con nombre (keyword arguments), sin que tengas que declararlos uno por uno.

El nombre kwargs es solo una convención (keyword arguments). Lo que realmente importa son los dos asteriscos **. Podrías llamarlo **opciones o **datos y funcionaría igual.


💻️ Ejemplo: **kwargs

def mostrar(**kwargs):
    print(kwargs)

mostrar(nombre="Ana", edad=30, ciudad="CDMX")
# {'nombre': 'Ana', 'edad': 30, 'ciudad': 'CDMX'}

Dentro de la función, kwargs es un diccionario normal: las claves son los nombres de los argumentos y los valores son lo que les pasaste. 

def saludar(**kwargs):
    for clave, valor in kwargs.items():
        print(f"{clave}: {valor}")

saludar(nombre="Ana", edad=30)
# nombre: Ana
# edad: 30
📝 Nota:
  1. Las claves de kwargs siempre son strings.
  2. Si no pasas ningún argumento con nombre, kwargs es un diccionario vacío ({}), no None.
  3. No puedes repetir un argumento: si nombre ya se pasó como parámetro normal, pasarlo otra vez en **kwargs lanza TypeError.

📦 Desempaquetar un diccionario

El ** también funciona al revés: al llamar una función, desempaqueta un diccionario en argumentos con nombre. 

def presentar(nombre, edad):
    print(f"{nombre} tiene {edad} años")

datos = {"nombre": "Ana", "edad": 30}
presentar(**datos)
# Ana tiene 30 años

Es equivalente a presentar(nombre="Ana", edad=30).

⚡ super() en herencia múltiple

En herencia múltiple, llamar manualmente a cada padre puede ejecutar el mismo __init__ más de una vez (o dejar clases sin inicializar). super() con **kwargs hace que cada clase se ejecute exactamente una vez, siguiendo el MRO.

Python ejemplo 
class Empleado:
    def __init__(self, nombre, salario, **kwargs):
        # "nombre" y "salario" se consumen aquí, en la firma.
        # Todo lo demás (especialidad, experiencia) queda dentro de kwargs.
        super().__init__(**kwargs)  # reenvía solo el resto a la siguiente
		                            # clase del MRO (Tecnico)
        self.nombre = nombre
        self.salario = salario


class Tecnico:
    def __init__(self, especialidad, experiencia, **kwargs):
        # "especialidad" y "experiencia" se consumen aquí.
        # En este punto kwargs ya llega vacío,
		# nombre y salario fueron consumidos por Empleado.
        super().__init__(**kwargs)  # reenvía un diccionario vacío a object,
		                            # que no acepta argumentos
        self.especialidad = especialidad
        self.experiencia = experiencia


class EmpleadoTecnico(Empleado, Tecnico):
    def __init__(self, **kwargs):
        # Recibe los 4 argumentos con nombre empaquetados en kwargs:
        # {"nombre": ..., "salario": ..., "especialidad": ..., "experiencia": ...}
        # Solo acepta argumentos con nombre (por eso no se pueden pasar posicionales).
        super().__init__(**kwargs)  # **kwargs desempaqueta el diccionario en
		                            # argumentos con nombre


# MRO: EmpleadoTecnico -> Empleado -> Tecnico -> object
#
# Flujo de kwargs:
#
# EmpleadoTecnico:
#	recibe:
#	  {"nombre"="Carlos Ramírez", "salario"=18000, "especialidad"="Electrónica", "experiencia"=4}
#	consume:
#	  No consume nada
#	reenvía a Empleado:
#	  {"nombre"="Carlos Ramírez", "salario"=18000, "especialidad"="Electrónica", "experiencia"=4}
#			
# Empleado:
#   recibe de EmpleadoTecnico:
#	  {"nombre"="Carlos Ramírez", "salario"=18000, "especialidad"="Electrónica", "experiencia"=4}
#	consume:
#	  nombre, salario
#	reenvía a Tecnico:
#	  {"especialidad"="Electrónica", "experiencia"=4}
#			
# Tecnico
#   recibe de Empleado:
#	  {"especialidad"="Electrónica", "experiencia"=4}
#	consume:
#	  especialidad y experiencia
#	reenvía a object:
#	  {} (vacío)
#
#   object:
#	  recibe: nada (correcto)
		
empleado = EmpleadoTecnico(
    nombre="Carlos Ramírez",    # los argumentos con nombre se empaquetan en kwargs
    salario=18000,
    especialidad="Electrónica",
    experiencia=4)

print(EmpleadoTecnico.__mro__)
salida 
(<class '__main__.EmpleadoTecnico'>, <class '__main__.Empleado'>, <class '__main__.Tecnico'>, <class 'object'>)

⚙️ Cómo funciona:

  1. El orden de resolución de métodos (MRO) de EmpleadoTecnico es:
    EmpleadoTecnico → Empleado → Tecnico → object.
    Puedes verlo con EmpleadoTecnico.__mro__.
  2. EmpleadoTecnico.__init__ recibe todos los argumentos en kwargs y los pasa con super().__init__(**kwargs).
  3. Empleado.__init__ toma nombre y salario, y el resto (especialidad, experiencia) sigue en kwargs hacia Tecnico.
  4. Tecnico.__init__ toma especialidad y experiencia, y le pasa un kwargs vacío a object.

🔍 Detalle sobre super() y el MRO

super() no significa "mi clase padre", sino "la siguiente clase en el MRO del objeto real". Por eso, dentro de Empleado, super().__init__ llama a Tecnico.__init__ (no a object) cuando el objeto es un EmpleadoTecnico.
Si creas un Empleado solo, su MRO es Empleado → object, y ahí sí llama a object.__init__. 

Empleado.__mro__          # (Empleado, object)
EmpleadoTecnico.__mro__   # (EmpleadoTecnico, Empleado, Tecnico, object)

🗄️ Datos sobre object

  • object es la raíz de toda jerarquía de clases y siempre va último en el MRO.
  • Es el destino final de la cadena de super().__init__(**kwargs).
  • No acepta argumentos en __init__, por eso kwargs debe estar vacío al llegar a él.
⚖️

Comparativa

Composición vs Herencia

Ambos mecanismos sirven para reutilizar código, pero con filosofías distintas: la herencia define lo que un objeto es, la composición define lo que un objeto tiene.

Ventajas y Desventajas

Herencia

La gran ventaja es la reutilización automática de código y el polimorfismo natural: una subclase obtiene todo del padre sin esfuerzo adicional, y puede usarse donde se espere el tipo base. Su desventaja es el acoplamiento fuerte que genera: un cambio en la superclase puede romper todas las subclases, y las jerarquías profundas se vuelven difíciles de seguir y mantener.

Composición

Su fortaleza está en el bajo acoplamiento y la flexibilidad: los objetos internos pueden cambiarse en tiempo de ejecución y cada clase tiene una responsabilidad clara. La contrapartida es que requiere delegar explícitamente las llamadas a los objetos contenidos, lo que puede resultar más verboso.

Tabla comparativa

Criterio Herencia Composición
Relación "es un" "tiene un"
Acoplamiento Alto — el hijo depende del padre Bajo — en Python se trabaja con duck typing
Flexibilidad Estática — fija al definir la clase Dinámica — cambiable en ejecución
Reutilización Automática — el hijo hereda todo Explícita — hay que delegar
Jerarquías Pueden volverse profundas y frágiles Se mantienen planas
Riesgo principal Clase base frágil Delegación verbosa
Polimorfismo Natural mediante sobreescritura Requiere diseño adicional
Cuándo usarla Relación "es un" genuina y estable Reutilizar comportamiento sin identidad de tipo
El regla general del diseño orientado a objetos es: favorecer la composición sobre la herencia. No porque la herencia sea mala, sino porque la composición es más robusta por defecto, y la herencia debe reservarse para cuando la relación conceptual entre las clases lo justifica de verdad.
